# Team protocol

How an agent team builds a system from a spec, with the human at the boundaries. Reduced from the full protocol for small projects.

### Roles

| Role | May | May not |
|---|---|---|
| **LEAD** (one session) | read SPEC.md twice; plan; create one worktree per team; run the teams' loops in parallel, spawning TESTER, CODER, REVIEWER in order inside each; run the gates; write `reports/<team>-phase-N.md` and DECISIONS entries; commit; open and, when told, merge the pull requests | write production code or tests |
| **TESTER** | write tests only, from the spec's acceptance criteria, plus the scaffolding strictly needed to run them; end with a TEST BRIEF (each test, what it asserts, how to run it) | touch production code, build logic or configs beyond test dependencies |
| **CODER** | make the TEST BRIEF pass with the minimum code that respects SPEC.md; verify library versions against the official docs; record deviations | modify any test or the contract; if a test cannot pass without contradicting the spec, stop and report |
| **REVIEWER** (read-only) | check the phase diff against SPEC.md: patterns, versions, secrets, magic values, test edits by the coder, spec-vs-code drift, DECISIONS updated; report findings, blocking first, with file and line | change anything |
| **HUMAN** | approve the spec; merge pull requests; answer escalations; add feedback rows to SPEC §9 | edit tests to unblock |

Segregation is the point: the tester does not know how it will be coded; the coder is bound by the tests; the reviewer is a second opinion with the power to block. Blocking findings on tests go back to the tester; on code, to the coder; then re-review once.

### The loop, per phase

1. TESTER → tests red, committed as `test(<team>-N): …`; the lead runs them and confirms they fail for readable reasons.
2. CODER → `feat(<team>-N): …` until green; no test edits.
3. REVIEWER → findings. **Blocking and security findings are fixed in the phase, once; everything else goes to `BACKLOG.md`.** No second tester-coder round for non-blocking findings.
4. LEAD → gate command; report (tests written with their red output, code added, findings and resolution, gate output, time spent, left red and why); decision files; pull request.
5. Next phase without waiting, unless a stop condition fires.

**Decisions and the spec.** One file per decision, `docs/decisions/D-NNN-slug.md` (what, why, alternatives, consequences), ids given by the lead; `DECISIONS.md` is an index generated by `make decisions`. Teams never edit SPEC §9 or §10; the lead writes them on `main` when it merges, from the team's report. Two branches never touch the same file.

**Git rules, in every prompt:** never amend, reset, rebase or stash; commit forward only; never push to `main`.

**Messages to agents.** Decisions are settled before an agent starts; nothing new reaches an agent mid-task. What comes up waits for its next phase or goes to `BACKLOG.md`.

**Deliverables grow with the work.** The README skeleton, the time log and the transcript start with the walking skeleton and are extended at every merge, never written at the end.

### Walking skeleton first, then parallel teams, one lead

One LEAD session. Before any team starts, one CODER lays down on `main` the **walking skeleton**: module, the interfaces of SPEC §5 as a package, config loader with validation, lint configuration, Makefile, a stub `cmd/` that serves `/health` over TLS and one real lookup end to end, compose with the api and its database, and the acceptance suite (red except the slice that runs). From then on every merge is checked by real acceptance tests, and whatever the clock stops on is a service that runs.

Then the lead creates one git worktree per team defined in SPEC §3 on its own branch and spawns every team's TESTER at once, one per worktree, never one tester for all teams. Each team is one MVP phase: its TESTER → CODER → REVIEWER loop deepens its area behind the interfaces; the delivery team wires the real implementations into `cmd/` as the others merge. No team waits on another: a team blocked on a merge pulls forward the next phase's work that does not depend on it. Phase 2 work that only depends on names frozen in the spec (metric names, labels, cert SANs, network and service names, endpoints) starts in parallel from the beginning in its own team; its only integration check against the live service happens once, after the wiring.

Every agent logs its own work: the lead writes the conversation with the human to `docs/agents/logs/lead.md` and each prompt it gives a subagent, with the answer, to `docs/agents/logs/<team>/lead-phase-N.md`; each TESTER, CODER and REVIEWER appends to `docs/agents/logs/<team>/<role>-phase-N.md` the prompt it received, the actions it took (files, commands, results) and its final output (TEST BRIEF, deviations, findings). These logs are the record of how the system was built, written as the work happens, never reconstructed afterwards. Every entry starts with a timestamp read from the clock at the moment of writing (`date -u +%Y-%m-%dT%H:%M:%SZ`), never estimated: when the prompt was received, when each action ran, when the output was written.

The split into teams is written in the spec (SPEC §3): one team per area with its own package boundary and its own test suite; the delivery team owns the walking skeleton, compose, CI and the final wiring.

### Stop conditions

The same test red after two CODER attempts; a required tool or version unavailable; a spec contradiction the docs cannot resolve; any destructive action (force-push, deleting data) outside scope: ask first. At the end of the last phase each lead writes `reports/<team>-final.md`: phases, green/red, deviations with reason, measured numbers, exact commands, what it would improve.

### Canonical prompts

**Lead (one session):**
```
SPEC.md is approved. You are the lead of the agent team that implements it, per docs/TEAM-PROTOCOL.md. Read SPEC.md twice, then docs/RULES.md and docs/TEAM-PROTOCOL.md. You do not write production code or tests: you plan, delegate, verify, report and commit. The box is 90 minutes and started at <HH:MM>: the walking skeleton, phase 1 (MVP) and phase 2 (demo) all inside it; phase 1 is what is graded, so it closes first. Milestones: skeleton on main by +10; all five teams' tests red by +20; A, B, D green and merged by +55; wiring, compose up and acceptance green by +70; make ci and the workflow green by +80; README, time log, transcript, tag by +90. Report the elapsed minutes at every gate. If a team is not green by +55, merge what is green and move the rest to BACKLOG.md; nothing from phase 2 merges before phase 1 is closed.
First, one CODER lays down the walking skeleton on main as §3 defines it (module, ports, config, lint config, Makefile, stub cmd/ serving /health over TLS and one real lookup end to end, compose with api and postgres, acceptance suite); commit it. Then create one git worktree per team on its own branch and spawn every team's TESTER at once, one per worktree, never one tester for all teams. TESTER and CODER on sonnet, REVIEWER on opus. Give each subagent only its team's sections of SPEC.md and the interface files, not the whole spec; the versions in SPEC §4 are already verified, subagents use them and do not check docs again. Each team runs one MVP phase: TESTER (exactly the tests in SPEC §6 for its area, red, TEST BRIEF) → CODER (minimum code, no test edits, versions from SPEC §4) → REVIEWER (read-only; blocking and security findings fixed once in the phase, everything else to BACKLOG.md) → gate, reports/<team>-phase-N.md, decision files in docs/decisions/, pull request against main. The delivery team wires real implementations into cmd/ as the others merge, runs make ci, adds the CI workflow and pushes; the first run must be green. No team waits on another; pull forward independent work. Never amend, reset, rebase or stash; say so in every subagent prompt. Settle decisions before an agent starts; nothing new reaches an agent mid-task. Start the README skeleton, the time log and the transcript with the walking skeleton and extend them at every merge.
Log the conversation with me in docs/agents/logs/lead.md as you go, each prompt you give a subagent and its answer in docs/agents/logs/<team>/lead-phase-N.md, and require every subagent to log its own prompt, actions and output in docs/agents/logs/<team>/<role>-phase-N.md, every entry timestamped from the clock (date -u), never estimated.
Stop conditions: same test red after two CODER attempts; missing tool or version; a spec contradiction the docs cannot resolve; any destructive action outside scope (ask first). Allowed: git (branches, worktrees, pull requests; never push to main), go, make, docker. No secrets. Tell me when a team is green so I can merge. Start with the walking skeleton.
```

**Tester:**
```
Write only the tests SPEC §6 lists for Team <X> Phase N, nothing more. Never amend, reset, rebase or stash; commit forward only. Do not write or modify production code, build logic or configs beyond test dependencies. Every test must fail now for a readable reason. Verify test-library versions against the official docs before adding them. End with a TEST BRIEF: each test, what it asserts, how to run it. Before finishing, write docs/agents/logs/<team>/tester-phase-N.md, every entry timestamped from the clock (date -u) when it happens, with the prompt you received, the actions you took (files, commands, results) and the TEST BRIEF.
```

**Coder:**
```
Make the tests in the TEST BRIEF pass with the minimum production code that respects SPEC.md and docs/RULES.md. You must not modify any test or the OpenAPI contract. Never amend, reset, rebase or stash; commit forward only. Verify every dependency version against the official docs before adding it; latest stable. No secrets, no magic values: every number comes from config with the spec's default. If a test cannot pass without contradicting the spec, stop and report instead of changing the test. Before finishing, write docs/agents/logs/<team>/coder-phase-N.md, every entry timestamped from the clock (date -u) when it happens, with the prompt you received, the actions you took (files, commands, results) and your deviations.
```

**Reviewer:**
```
Read-only. Check Team <X> Phase N against SPEC.md and docs/RULES.md: the brief's numbers respected, versions pinned and current, no secrets, no magic values, no test edits by the coder, spec-vs-code drift, DECISIONS updated, timings reported. Report findings only, blocking and security first, with file and line; mark each finding blocking or backlog; change nothing except docs/agents/logs/<team>/reviewer-phase-N.md, where you write, every entry timestamped from the clock (date -u) when it happens, the prompt you received, what you checked and your findings.
```

### Human feedback channel

SPEC §9: every human review adds a dated, numbered row (F-nnn) with what, where it applies and status; each lead reads §9 at every phase start and lists the rows addressed in its report.

### Merging

One pull request per team per phase against `main`, opened by the lead and merged by the human (or by the lead when the human says so), the delivery team's wiring last; CI green is the required check once the workflow exists.
